## Document purpose

This document defines the product scope, functional requirements, MVP
boundaries, technical direction, data requirements, acceptance criteria
and phased implementation roadmap for Nivesh.

It is intended to be used as:

-   The product baseline for the owner and development team.
-   A reference for coding agents implementing individual modules.
-   A source for creating engineering epics, user stories and acceptance
    tests.
-   A guardrail against premature implementation of advanced features
    before the data and analytics foundations are reliable.

The document is deliberately research-first. Trading and public-facing
recommendations are included in the long-term product vision, but are
not prerequisites for the first usable release.

# 1. Executive summary

Nivesh is an investment research and intelligence platform for Indian
investors. It brings together mutual fund analysis, equity research,
market intelligence, screening, portfolio tracking, alerts, AI-assisted
research and, eventually, broker integration.

The platform should help users answer six questions:

1.  What investment opportunities should I investigate?
2.  Is this mutual fund or company fundamentally attractive?
3.  How does it compare with relevant peers and benchmarks?
4.  What risks, valuation concerns or warning signs should I understand?
5.  How do my investments behave together as a portfolio?
6.  What has changed since I last reviewed an investment?

Nivesh should not be a simple collection of charts and financial ratios.
It should be a research workflow in which every important metric has a
defined methodology, every displayed value has an as-of date, and every
AI-generated insight can be traced to supporting data or source
documents.

## 1.2 Product principles

1.  **Data accuracy before feature quantity.** A smaller set of reliable
    metrics is more valuable than a large set of questionable metrics.
2.  **Deterministic calculations.** Financial metrics must be calculated
    by tested code, not generated by an LLM.
3.  **Traceability.** Store source, publication date, observation date,
    calculation version and data freshness.
4.  **Comparable analysis.** Comparisons must use suitable benchmarks,
    comparable periods and asset-class-appropriate methodologies.
5.  **Explainable signals.** Every alert or signal must show the rule
    and values that triggered it.
6.  **Evidence-based AI.** AI must retrieve approved data and source
    documents, cite evidence and disclose uncertainty.
7.  **Modular architecture.** Keep clear domain boundaries without
    prematurely introducing distributed-system complexity.
8.  **Research before execution.** Trading is isolated from analytics
    and requires separate security and compliance controls.
9.  **Point-in-time correctness.** Historical testing must avoid
    look-ahead and survivorship bias.
10. **Multi-user readiness.** User-owned portfolios, watchlists, alerts
    and research notes must be isolated from the beginning.

# 2. Goals, non-goals and target users

## 2.1 Product goals

-   Provide comprehensive Indian mutual fund and listed-equity research.
-   Calculate performance, risk, fundamental and valuation metrics
    consistently.
-   Enable fund and stock discovery through configurable screeners.
-   Compare investments against appropriate peers and benchmarks.
-   Track user portfolios across mutual funds and direct equities.
-   Identify underlying exposure, overlap and concentration.
-   Monitor changes through watchlists and configurable alerts.
-   Provide AI-assisted analysis grounded in verified financial data.
-   Add historical strategy testing and broker connectivity in later
    phases.
-   Support a future public multi-user product.

## 2.2 Initial non-goals

The MVP will not attempt to:

-   Provide live exchange-grade trading data unless a suitable provider
    and licence are secured.
-   Execute live trades.
-   Operate an automated trading strategy.
-   Publish personalized investment advice.
-   Guarantee investment outcomes or predict future returns.
-   Replace official exchange, AMC or company disclosures.
-   Provide complete tax filing or tax advice.
-   Cover every international market or asset class.
-   Implement institutional portfolio accounting in the first release.

## 4.2 M02 --- Mutual Fund Research

### MF-01: Scheme master

Maintain a canonical scheme record with:

-   Scheme code and scheme identifiers.
-   Scheme name and AMC.
-   Category and subcategory.
-   Direct or regular plan.
-   Growth or IDCW option.
-   Open, closed or merged status.
-   Scheme launch date.
-   Benchmark and effective dates of benchmark mapping.
-   Current and historical fund manager assignments.
-   AUM and reporting date.
-   TER and effective date.
-   Exit load and effective date.
-   Riskometer and disclosure date.
-   Source and last-updated timestamp.

**Rules:**

-   Direct and regular plans must remain distinct.
-   Growth and IDCW options must remain distinct.
-   Scheme mergers and changes must be traceable.
-   Historical classifications and benchmark mappings must not be
    overwritten without history.

**Priority:** P0.

### MF-02: NAV history

-   Ingest daily NAV observations.
-   Retain source and source publication/ingestion timestamps.
-   Validate duplicates and abnormal movements.
-   Detect missing expected observations.
-   Support historical NAV queries.
-   Make raw NAV observations immutable; corrections must be represented
    with an audit trail or versioned correction record.
-   Distinguish non-business days from missing data.

**Priority:** P0.

### MF-03: Performance analytics

Calculate and display:

-   Absolute return.
-   CAGR.
-   Rolling returns.
-   Calendar-year returns.
-   Monthly returns.
-   SIP XIRR.
-   Benchmark returns.
-   Category average and median.
-   Benchmark outperformance.
-   Rolling consistency.
-   Return distribution and quartile ranking.

Suggested periods:

-   1 month, 3 months, 6 months.
-   1 year, 2 years, 3 years.
-   5 years, 7 years, 10 years.
-   Since inception, where meaningful.

Rolling-return analysis should include:

-   Mean.
-   Median.
-   Minimum and maximum.
-   Standard deviation.
-   Percentage of windows beating benchmark.
-   Percentage of windows exceeding configurable return thresholds.
-   Distribution chart.
-   Window count and observation period.

and consistency.

  -----------------------------------------------------------------------
  Metric                              Core definition / requirement
  ----------------------------------- -----------------------------------
  CAGR                                Compounded annualized return over
                                      elapsed time

                                      cash flows

## 21.1 Instrument seed data and reference-data bootstrap

**Objective:** Ensure that every supported stock, mutual fund, index and related instrument has a consistent initial record and enough historical reference data to make the research experience useful from the first day.

The term *seed data* has two distinct meanings in Nivesh and they must not be confused:

1. **Reference/master seed data:** Instrument identity, exchange, symbol, ISIN, scheme code, category, benchmark mapping, currency, country, sector and other relatively stable metadata.
2. **Historical data bootstrap:** Initial download of available historical NAV, price, index, corporate-action, financial-statement or holdings records.

The application must support both.

### Requirements

- Maintain a canonical instrument registry across stocks, mutual funds, ETFs, indices and benchmarks.
- Each instrument must have a stable internal Nivesh ID that is independent of provider-specific symbols or identifiers.
- Store external identifiers separately, including exchange symbol, ISIN, AMFI scheme code, provider instrument ID and vendor-specific code.
- Support multiple listings or identifiers for the same economic issuer where applicable.
- Seed a new instrument when it is first added to a watchlist, portfolio, comparison or research workspace.
- When an instrument is seeded, determine which data sets are required for its asset class and market.
- Bootstrap the available historical data from configured sources.
- Track the earliest and latest available observation for each data set.
- Track whether the bootstrap is pending, running, completed, partially completed or failed.
- Allow a user or administrator to request a backfill for a selected instrument and date range.
- Make backfills idempotent: rerunning the same request must not create duplicate observations.
- Preserve source provenance and ingestion timestamps.
- Display data coverage and limitations on the instrument detail page.
- Allow administrators to seed a predefined universe in bulk, such as Nifty 50, S&P 500, STI constituents or a selected mutual fund category.
- Support incremental updates after the initial historical bootstrap.

### Seed profiles

Define configurable seed profiles by instrument type:

| Seed profile | Required initial data |
|---|---|
| Indian stock | Company master, exchange identifiers, daily OHLCV, corporate actions, available financial statements, sector/industry |
| International stock | Issuer master, exchange/ticker, MIC or exchange identifier, currency, daily OHLCV, available corporate actions and fundamentals |
| Mutual fund | Scheme master, AMC, category, plan/option, NAV history, benchmark mapping, available manager history |
| Index | Index master, country, provider, currency, price/total-return classification, historical index values |
| ETF | Instrument master, exchange identifiers, daily prices, corporate actions, available holdings and benchmark |

### User experience

An instrument page must clearly distinguish:

- Data available from source.
- Data ingested by Nivesh.
- Last successful refresh.
- Historical coverage start and end.
- Missing or unsupported fields.
- Whether the data is delayed, end-of-day or real-time.

### Acceptance criteria

1. Adding a supported instrument initiates or schedules its required seed workflow.
2. A seed workflow can be retried without duplicates.
3. The UI shows seed status and data coverage.
4. A partial seed does not make the instrument appear fully populated.
5. Administrators can bulk-seed a configured universe.
6. A user can request a historical backfill without manually editing database records.
7. Every seeded data set has source and timestamp metadata.

**Priority:** P0 for master data and Indian MF/stock bootstrap; P1 for broad universe seeding; P2 for multi-country bulk universe expansion.

### Example strategy concepts

These are example configurations to be implemented and tested; they are not investment recommendations.

**1. RSI mean-reversion strategy**

- Entry candidate: RSI falls below a configured threshold.
- Optional confirmation: price closes back above the threshold or a short-term moving average.
- Exit: RSI reaches an upper threshold, a stop is hit or a maximum holding period is reached.
- Parameters: RSI period, lower threshold, upper threshold, stop percentage, holding period.

**2. Bollinger Band re-entry strategy**

- Entry candidate: price closes below the lower band and subsequently closes back inside the bands.
- Optional filter: market trend or RSI condition.
- Exit: middle band, upper band or configured risk rule.
- Parameters: moving-average period, standard-deviation multiplier, confirmation rule.

**3. EMA crossover strategy**

- Entry candidate: short-period EMA crosses above long-period EMA.
- Exit candidate: short-period EMA crosses below long-period EMA.
- Optional filters: ADX threshold, volume confirmation, broad-market trend.
- Parameters: fast EMA, slow EMA, ADX period and threshold.

**4. SMA trend-following strategy**

- Entry candidate: price closes above a selected SMA and the SMA slope is positive.
- Exit candidate: price closes below the selected SMA or a risk rule is triggered.
- Parameters: SMA period, slope lookback, stop and exit rule.

**5. MACD momentum strategy**

- Entry candidate: MACD line crosses above signal line.
- Optional filter: MACD above/below zero line and volume confirmation.
- Exit candidate: reverse crossover or risk rule.

**6. Candlestick confirmation strategy**

- Entry candidate: a selected bullish or bearish pattern is detected near a defined support/resistance region.
- Confirmation: next candle or subsequent price action meets a configurable rule.
- Optional filters: RSI, volume, EMA trend and ATR.
- Exit: pattern invalidation, stop, target or time-based exit.

**7. Multi-indicator confluence strategy**

- Combine trend, momentum, volatility and volume conditions.
- Allow required conditions and optional weighted conditions.
- Show which conditions passed or failed for every signal.
- Avoid opaque scores without a visible calculation.

### Strategy engine requirements

- Strategies must run on a common interface.
- Support daily timeframes initially.
- Support intraday only when licensed data and reliable session handling are available.
- Calculate indicators using a shared indicator library.
- Cache or precompute indicators for frequently used instruments.
- Support parameterized strategies.
- Support long-only initially; short selling and derivatives require separate market rules and risk controls.
- Support watchlist scans and configured universes.
- Generate candidate signals without placing orders.
- Persist strategy runs and their input data references.
- Provide deterministic replay for a historical date range.
- Track strategy version and indicator version.
- Display entry, exit and invalidation reasons.
- Include trading costs, slippage and corporate actions in backtests.
- Prevent look-ahead bias by ensuring a signal only uses data available at the signal timestamp.

## 21.5 User-added Python strategy plugins

**Objective:** Allow an advanced user or developer to add a strategy by placing a `.py` file in a configured strategy directory. Nivesh should discover the strategy and expose its metadata and parameters in the UI.

This must use a controlled plugin contract. Nivesh must never blindly execute arbitrary Python code from an untrusted directory.

### Desired user workflow

1. User adds a strategy Python file to the configured plugin directory.
2. User opens Strategy Lab and selects **Refresh strategies** or the application discovers the file during a controlled scan.
3. Nivesh validates the file and reads its declared metadata.
4. The strategy appears in the UI with name, description, supported markets, timeframes and parameters.
5. User selects the strategy and configures parameters.
6. User runs validation or a backtest.
7. Nivesh displays validation results and strategy metrics.
8. The user can save a configuration and rerun it later.

### Recommended directory structure

```text
nivesh/
  strategies/
    built_in/
      rsi_mean_reversion.py
      ema_crossover.py
      bollinger_reentry.py
    user/
      my_custom_strategy.py
    manifests/
      strategy_registry.json
```

The exact directory can be configurable. The application should not require users to edit core application code to add a strategy.

### Strategy plugin contract

A strategy plugin should expose:

- Stable strategy ID.
- Human-readable name.
- Description.
- Version.
- Author.
- Supported asset classes.
- Supported markets.
- Supported timeframes.
- Parameter definitions.
- Required input columns.
- Entry/exit or signal-generation implementation.
- Optional risk-management hooks.
- Optional plotting/annotation metadata.

Conceptual example:

```python
from nivesh_strategy_sdk import Strategy, StrategyMetadata, Parameter

class MyCustomStrategy(Strategy):
    metadata = StrategyMetadata(
        id="my_custom_strategy",
        name="My Custom Strategy",
        version="1.0.0",
        description="Example custom strategy",
        asset_classes=["equity"],
        markets=["IN", "US"],
        timeframes=["1d"],
        parameters=[
            Parameter(name="rsi_period", type="int", default=14, minimum=2, maximum=100),
            Parameter(name="oversold", type="float", default=30, minimum=1, maximum=50),
        ],
    )

    def generate_signals(self, data, params, context):
        # Return a documented signal structure.
        # Do not place broker orders from this method.
        ...
```

This is an illustrative interface. The final SDK contract should be implemented and documented before third-party strategy development begins.

### Discovery and validation

- Scan only configured plugin directories.
- Validate Python syntax before registration.
- Validate required metadata and method signatures.
- Reject duplicate strategy IDs or incompatible versions.
- Validate declared parameter types and ranges.
- Run a small test dataset before making a strategy available.
- Record validation logs and errors.
- Allow a plugin to be disabled without deleting its source file.
- Support explicit refresh and optional controlled startup discovery.
- Show plugin file path and version in the administration UI.
- Do not import or execute the plugin in the main API process.

### Security and execution isolation

Python files can execute arbitrary operating-system commands. Therefore:

- Treat user-provided strategy files as untrusted code.
- Execute strategies in a separate worker process or isolated container.
- Use a non-privileged operating-system user.
- Restrict filesystem access.
- Restrict network access by default.
- Apply CPU, memory and execution-time limits.
- Do not expose broker credentials, application secrets or database administrator credentials to strategy code.
- Provide read-only market-data inputs.
- Return structured signals rather than allowing direct database writes.
- Never allow strategy code to place live orders directly.
- Require explicit administrator approval for plugins in a shared/public deployment.
- Log strategy execution, errors and resource usage.

### UI requirements

The Strategy Lab should show:

- Available strategies.
- Built-in versus user-added source.
- Description and version.
- Supported markets and asset classes.
- Parameter form generated from metadata.
- Validation status.
- Backtest/run action.
- Execution history.
- Error details for failed validation.
- Enable/disable control where the user has permission.

### Acceptance criteria

1. A valid `.py` plugin can be discovered without modifying application source code.
2. The UI renders the strategy metadata and parameter controls.
3. An invalid plugin is rejected with a useful error.
4. Duplicate strategy IDs are handled safely.
5. A plugin runs outside the main API process.
6. Plugin execution cannot access broker secrets.
7. Plugin output follows a documented signal schema.
8. A strategy version is retained with every run.
9. A plugin can be disabled and rediscovered after correction.

**Priority:** P2. Build the plugin SDK after the built-in strategy engine and backtest contract are stable.

## 21.11 Data-model migration, rebuild and reprocessing framework

- Use version-controlled database migrations.
- Maintain migration history.
- Support upgrade and documented recovery procedures.
- Preserve raw source data.
- Version normalization and transformation logic.
- Version calculation methodologies.
- Support reprocessing by entity, date range, dataset and source.
- Support dry-run mode.
- Show expected affected record counts before execution.
- Show progress, logs, warnings and errors.
- Support resumable jobs.
- Make jobs idempotent.
- Use staging tables or shadow tables for large rebuilds where appropriate.
- Validate row counts and financial invariants before publishing rebuilt data.
- Support atomic swaps or controlled publication where appropriate.
- Retain previous published results until the new result passes validation.
- Provide a rollback or restore procedure.
- Require elevated permission for destructive or broad rebuilds.
- Never provide a general-purpose “drop all and recreate” action in the normal user interface.

### Reprocessing examples

- Add a new normalized financial statement field and backfill historical statements.
- Correct a corporate-action adjustment rule and recompute affected adjusted prices.
- Change a rolling-return calculation and regenerate historical metrics.
- Add a new benchmark mapping and recompute fund comparisons.
- Change the portfolio valuation logic and rebuild daily snapshots.
- Add a new manager-history field and backfill available historical assignments.

### Job model

A rebuild/reprocessing job should store:

- Job ID.
- Job type.
- Target dataset/entity.
- Date range.
- Input source/version.
- Transformation or calculation version.
- Requested by.
- Requested timestamp.
- Dry-run flag.
- Status.
- Progress counters.
- Validation results.
- Error summary.
- Start and completion timestamps.
- Published output version.

### Administration UI

Provide:

- Migration status.
- Data pipeline status.
- Reprocessing job creation.
- Scope selection.
- Dry-run preview.
- Confirmation step.
- Job progress.
- Validation report.
- Failure details.
- Retry and rollback controls subject to permissions.

### Acceptance criteria

1. Schema changes are applied through versioned migrations.
2. Derived data can be rebuilt from retained canonical/raw inputs.
3. A dry run shows the intended scope before execution.
4. Reprocessing is idempotent and resumable.
5. Existing published data remains available until replacement data passes validation.
6. Every rebuild records the code/methodology version used.
7. Destructive operations require elevated authorization and explicit confirmation.

**Priority:** P0 for migrations and idempotent backfills; P1 for administrative rebuild workflows; P2 for sophisticated shadow rebuilds and rollback automation.

## 21.12 Historical mutual fund manager data

**Objective:** Maintain a date-aware history of mutual fund managers and their scheme assignments so that performance analysis can be attributed to the correct manager tenure.

### Requirements

- Store manager master records with stable internal IDs.
- Store manager names and available public profile details.
- Store scheme-to-manager assignments.
- Store assignment start date and end date.
- Support multiple managers assigned to a scheme at the same time.
- Support role labels such as lead manager, co-manager or debt manager when the source provides them.
- Store the source document and disclosure date.
- Retain the date on which Nivesh learned about the assignment.
- Track corrections and conflicting disclosures.
- Preserve historical assignments after a manager leaves a scheme.
- Support manager changes, team changes and scheme mergers.
- Avoid assuming that a current manager managed the fund's entire history.

### Manager history analytics

- Scheme performance during a manager's tenure.
- Benchmark-relative return during tenure.
- Category-relative return during tenure.
- Risk-adjusted return during tenure.
- Drawdown during tenure.
- Manager's current and historical scheme assignments.
- Number of schemes managed concurrently.
- Equity/debt/hybrid category experience where source data supports it.
- Changes in performance before and after manager transition, with appropriate caution.

### Data limitations

- Public disclosures may not provide complete historical dates.
- Manager name variations must be resolved carefully.
- Joint management responsibilities may differ by asset class or mandate.
- Do not infer an exact start date from a factsheet publication date unless the source supports that interpretation.
- Mark unknown start/end dates as unknown rather than fabricating dates.

### Acceptance criteria

1. A scheme can have multiple manager assignments over time.
2. Historical assignments are not overwritten by current manager details.
3. Performance attribution uses the manager's actual available tenure.
4. Source and disclosure dates are retained.
5. Incomplete or uncertain history is visibly identified.

**Priority:** P1.

# 27. Final implementation guidance

The expanded vision is substantial. To keep development manageable:

1. Build a stable instrument registry and seed framework first.
2. Build reliable Indian market data ingestion and analytics.
3. Establish technical indicators as reusable functions.
4. Implement candlestick recognition as a deterministic engine.
5. Build the strategy runtime and backtest contract before accepting arbitrary plugins.
6. Add plugin discovery only after isolated execution is working.
7. Add portfolio daily snapshots only after transaction and corporate-action handling is dependable.
8. Implement broker read-only sync before considering order placement.
9. Build educational chat before complex autonomous agents.
10. Add agentic research only when the underlying APIs return reliable, traceable data.
11. Build report generation from the same analytics APIs used by the UI.
12. Treat data migrations, reprocessing and update support as core platform operations, not developer-only scripts.

**The central design rule remains unchanged:** Nivesh should have one trusted data and analytics foundation. The UI, reports, strategies, broker-connected portfolio views and AI assistant should all consume that same foundation rather than independently calculating or storing conflicting versions of financial facts.
